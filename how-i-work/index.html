Method

How the work gets made

Claude CodeDaily, 18 monthsSept 2026

Producing more is the easy half.

Every marketer now has the same leverage, so output stopped being the interesting number about a year ago. What separates one AI workflow from another is whether anybody has to read the output twice before it ships.

This is the part of my work that does not appear in a case study: the generator that writes the files, the checks that refuse to let them out, and the log of everything that got caught on the way.

What I do not do
Type most of it. I decide what it does and I own every decision in it, which is a different claim and the only one worth making.
What I built instead
An 892 line generator that produces 52 email files from one shell, a 14 check harness that blocks a deploy, and 1,135 lines of written rules so the same mistake cannot happen twice.
Why it matters
Volume without verification is just a faster way to ship something wrong. Everything below was caught by the system rather than by a person reading carefully.
01

The generator, never the file

Ten emails exist for the Payload build. Fifty two files exist on disk, because two of them branch across five industries. Nobody edits those files. They are output.

One Python file holds the shell, the components and the copy. Change the button helper and every button in all fifty two files changes. Change a subject line and the flow page that previews it fails its own check until it agrees.

The alternative is fifty two files that drift, which is not hypothetical. Four subject lines on a preview page went stale over about a dozen edits, and one of them was still displaying a raw merge token on a page whose entire claim was that it did not use them.

Six assertions run inside the generator itself. It will not write a file containing an unrendered token, an em dash, or an unreplaced sample key, because each of those has shipped before and each now has a line of code preventing it.

02

Fourteen things that stop a deploy

A Playwright harness runs against every page before anything is pushed. Not a linter. It opens a real browser, scrolls the whole page, and measures what actually rendered.

CheckWhat it catches
ContrastEvery text node against its resolved background, including gradient fills, at 4.5:1 or 3:1 by size
Type scaleAny rendered font size that is not one of the nine tokens
OverflowHorizontal scroll at 320, 375, 390, 768, 1024 and 1512
Image integrityDeclared aspect against the real file header, plus anything rendering above 1.0x and going soft
Copy driftEvery subject line in the generator must appear on the page that previews it, both directions
Unsourced claimsGreps customer copy for invented statistics: "nine times out of ten", "studies show", "N% of"
Unstyled classesAny class in the markup with no matching rule, which catches invented names and edits that silently failed
Dead anchorsResolves every #fragment against a real id in the target file, not just the path
Consent defaultFails the build if an opt in checkbox ever ships pre ticked
Repeated phrasesA 6-gram counter over the body text, so a summary summarises instead of pasting

Plus em dashes, dead file references, tag balance and console errors. The target is zero, not few.

03

What it actually caught

This is the part that matters. A checklist nobody fails is decoration.

01

A merge token, in the one build that claimed not to use them

The plain text version of an email was shipping a literal {eng} where a name belonged. The generator asserted on two other token shapes and neither catches a brace. Both renderers now assert on every sample key by name.

02

Every image on a page, stretched 2.1x

width:100% with an HTML height attribute and no height:auto means the height attribute wins. A 2160x1215 screenshot was drawing at 1030x1215 and the CSS looked correct. Now measured against the PNG header.

03

A statistic I made up

An email opened "nine times out of ten that is not disinterest." Nobody can source that. It is the same failure as a fabricated credential, in a package whose whole argument is that every figure is checkable.

04

Two CSS blocks that were never inserted

A build script matched an anchor with a leading space the file did not have. str.replace returns the string unchanged on a miss, so it reported success and the styles simply were not there. Every replace is asserted now.

04

So it cannot happen twice

Each of those is now a numbered entry in a written rule file that loads before any work on that project starts. Forty entries across 1,135 lines, and every one of them exists because something went wrong once.

That is the actual difference between running a lot of agents and getting a lot out of them. The model does not remember last Tuesday. The rules do.

It is also why the same mistake does not appear in two places. The image stretching bug was found on a portfolio page, and the rule that came out of it is why the same pattern was caught on the next build before it shipped.

# from the project rule file

25. An unasserted str.replace fails silently. It returns the string
    unchanged when the pattern misses, so the script reports success and
    the edit is simply absent. Assert every replace.

27. Invented class names render as nothing and QA did not catch it.
    The harness now fails on any class used in markup with no matching
    rule in that page's CSS.

Written in the second person, to the next session, by the one that got it wrong.
